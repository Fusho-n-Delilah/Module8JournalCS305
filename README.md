# Module 8 Journal CS305

I chose to include my Artemis Financial secure software project, or my final project. Artemis Financial was a financial services company that needed help improving the security of its web application. The main thing they wanted addressed was secure communication and data verification. Since they deal with sensitive financial information, the application needed to protect data while it was being transmitted and also have a way to verify that data had not been changed. For this project, I added HTTPS support and created a SHA-256 checksum endpoint so the application could return a secure hash value.

I think one thing I did well was not just running the vulnerability scan and stopping there. I actually looked through the results, worked through the dependency issues, and tried to understand what the findings meant. Some of the hardest parts were honestly the setup issues, like getting the Java version, Maven goals, OWASP Dependency-Check, and suppression file working correctly. It was frustrating at times, but it helped me understand that secure coding is not only about the code itself. It is also about dependencies, configuration, certificates, tools, and making sure everything still works after changes are made.

Secure coding matters because a single weak spot can turn into a much bigger problem for a company. If customer data is exposed or the application is not trustworthy, that can hurt the company financially and damage its reputation. Security adds value because it protects the users, protects the business, and makes the software more dependable overall.

I increased security in a few ways. I configured the application to use HTTPS, added the SHA-256 checksum functionality, updated dependencies, added Spring Security, and added logging so there would be better visibility into what the application is doing. In the future, I would use tools like OWASP Dependency-Check, Maven dependency reviews, OWASP guidance, and manual code review to find vulnerabilities and decide how to fix them. I would also make sure to look at whether each vulnerability actually applies to the application instead of just assuming every scanner result has the same level of risk.

To make sure the application was still functional and secure, I tested the /hash endpoint after refactoring the code and confirmed that it worked over HTTPS at https://localhost:8443/hash. After making changes, I reran the dependency scan to check whether I fixed the original problems or introduced new ones. That part was important because changing dependencies or security settings can easily break something if you do not test afterward.

The tools and practices from this project that I would use again include OWASP Dependency-Check, Maven, Java keytool, Spring Boot, Spring Security, HTTPS configuration, SHA-256 hashing, logging, and testing after refactoring. I also learned that it is important to read vulnerability reports carefully and understand the actual risk instead of just copying whatever the tool says.

For future employers, I could show this project as an example of how I can take an existing application, review it for security problems, make improvements, and verify that the changes work. It shows experience with secure communication, hashing, dependency scanning, vulnerability mitigation, and documenting the process. More importantly, it shows that I understand security as part of the development process, not just something that gets added at the end.
